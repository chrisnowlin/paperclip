# V2 local Splash and named AI accounts

Status: integrated implementation branch decision · 2026-09-26

## Decision

Use the existing `opencode_local` adapter for a dedicated `localSplash` profile. Its model is exactly `splash/incoai/Qwen3.8-27B-Splash`, routed through an isolated OpenCode configuration to Splash's OpenAI-compatible loopback API at `127.0.0.1:8000/v1`. This initial profile expects Splash's default unauthenticated loopback listener; a keyed listener needs a later explicit secret-backed binding. The profile pins OpenCode's primary, small, and built-in agent models to Splash and rejects extra CLI arguments that could replace its model or server. Each invocation uses a fresh temporary XDG config/cache home, while task-scoped OpenCode session data stays in a private directory under the current Paperclip instance root so a later turn can resume it. Temporary config is removed after the invocation; retained session data follows the instance lifecycle. Inherited paid-provider authentication and routing variables are masked, and the route fails if the selected model is absent at `/v1/models`. It does not start Splash, prepare weights, choose another local engine, or fall back to a paid provider. The local setup window lists Splash independently of `auth.json`, including while the server is offline or paid-provider discovery fails; it shows readiness separately, and the connection test fails until the model is visible on that endpoint. This route is local-only; a remote execution target must use a different explicitly configured model.

Keep Claude and OpenAI accounts in managed AI Connections. Create separate, clearly named accounts in the existing Apps/Connections UI, with the correct human audience and agent installation. Personal provider defaults remain one per company/user/provider; configure additional accounts as named connections with an intentionally narrow audience. Bind each paid agent deliberately through its existing `runtimeConfig.aiConnection` selection. Use a `shared` binding with an exact `connectionId` and `grantId` for an additional named account when the task's responsible user has access. Use `responsible_user` only when that user's provider default is intentionally the desired account. A coding pod continues to name agents. On task attachment, its activity entry records each role's selected route, including exact managed connection and grant IDs where available or an explicit unmanaged marker. Run attribution records the account actually used, so later agent setting changes remain distinguishable from the attachment decision. Neither record contains credentials. The issue's responsible user, account audience, agent installation, and model compatibility are checked at run time. A revoked or unavailable selected account blocks the run; it does not rotate to another account. Credential changes start a fresh provider session under the existing session identity contract.

V2 requires a sandboxed reviewer. Local Splash can be selected for the owner; an enabled pod rejects a `localSplash` reviewer even if that agent has a sandbox selected. Assign the reviewer to a separate sandbox-capable agent with its intended named AI Connection.

For local-trusted Claude subscription accounts, use isolated `CLAUDE_CONFIG_DIR` sign-in attempts when connecting the second account. Do not duplicate a host login or put tokens in project files. API keys remain encrypted in existing grants. This work does not create or test live paid accounts.

## Qualification requiring the operator

1. Free or provide adequate storage for Splash's prepared weight cache, then choose its destination with `SPLASH_WEIGHT_CACHE`. Current data-volume free space is about 15 GiB, while the cached Hugging Face package occupies about 16 GiB. Confirm Splash's actual preparation space requirement before running `splash serve`; do not redownload or delete cached files as an implicit setup step.
2. Start Splash explicitly in a terminal, wait for `Ready`, and verify `/v1/models` includes `incoai/Qwen3.8-27B-Splash`. The OpenCode setup window should show Splash without an `auth.json` entry even before startup, then change its readiness message. Test the route and a disposable task only after approving live model execution.
3. Connect and label each intended work/personal Claude or OpenAI account through AI Connections. For each coding-pod role, choose an agent and inspect its harness, model, named connection, audience, and installed-agent access before allowing work. Exercise a disposable issue with an explicit account binding and inspect run attribution. Revoke the chosen account in a disposable test to verify that the issue blocks without fallback.
4. Build and qualify the combined V2 app when it is safe to stop any running V2 process. `script/build_and_run.sh --build-only` stops `PaperclipStandaloneV2` before packaging, so it must not be run while another V2 task still owns that process. Verify bundle identity, ports, data paths, and V1 isolation with the existing smoke script. No V1 or V2 app was launched for this branch.

## Verification in this branch

The focused adapter tests use mock HTTP responses and never serve the model. Existing `server/src/__tests__/ai-connections.test.ts` covers named shared grants, private credential homes, provider defaults, and no automatic fallback after revocation. All 43 tests passed when Vitest was launched from a neutral temporary working directory with the repository root and test path supplied explicitly. Running that suite from this checkout makes seven OpenAI fixture cases encounter the host's `~/.codex/config.toml` provider override during the project-authentication conflict guard; the host file was not changed. The combined V2/Splash focused suites, repository typecheck, and Swift release build check integration without starting an agent. Live endpoint and account qualification are separate.
