# V2 local Splash and named AI accounts

Status: implementation branch decision · 2026-09-26

## Decision

Use the existing `opencode_local` adapter for a dedicated `localSplash` profile. Its model is exactly `splash/incoai/Qwen3.8-27B-Splash`, routed through an isolated OpenCode configuration to Splash's OpenAI-compatible loopback API at `127.0.0.1:8000/v1`. This initial profile expects Splash's default unauthenticated loopback listener; a keyed listener needs a later explicit secret-backed binding. The profile pins OpenCode's primary, small, and built-in agent models to Splash. It uses a fresh XDG configuration/data home per invocation, masks inherited paid-provider authentication and routing variables, and fails if the selected model is absent at `/v1/models`. It does not start Splash, prepare weights, choose another local engine, or fall back to a paid provider. The local setup window lists Splash independently of `auth.json`, including while the server is offline; it shows readiness separately, and the connection test fails until the model is visible on that endpoint. This route is local-only; a remote execution target must use a different explicitly configured model.

Keep Claude and OpenAI accounts in managed AI Connections. Create separate, clearly named accounts in the existing Apps/Connections UI, with the correct human audience and agent installation. Personal provider defaults remain one per company/user/provider; additional accounts must be named connections. Bind each paid agent deliberately through its existing `runtimeConfig.aiConnection` selection. Use a `shared` binding with an exact `connectionId` and `grantId` for a specific work or personal account when the task's responsible user has access. Use `responsible_user` only when that user's provider default is intentionally the desired account. A coding pod continues to name agents; its owner/reviewer agent identities and existing run attribution expose the account decision without a second credential store or a new task scheduler. The issue's responsible user, account audience, agent installation, and model compatibility are checked at run time. A revoked or unavailable selected account blocks the run; it does not rotate to another account. Credential changes start a fresh provider session under the existing session identity contract.

For local-trusted Claude subscription accounts, use isolated `CLAUDE_CONFIG_DIR` sign-in attempts when connecting the second account. Do not duplicate a host login or put tokens in project files. API keys remain encrypted in existing grants. This work does not create or test live paid accounts.

## Qualification requiring the operator

1. Free or provide adequate storage for Splash's prepared weight cache, then choose its destination with `SPLASH_WEIGHT_CACHE`. Current data-volume free space is about 15 GiB, while the cached Hugging Face package occupies about 16 GiB. Confirm Splash's actual preparation space requirement before running `splash serve`; do not redownload or delete cached files as an implicit setup step.
2. Start Splash explicitly in a terminal, wait for `Ready`, and verify `/v1/models` includes `incoai/Qwen3.8-27B-Splash`. The OpenCode setup window should show Splash without an `auth.json` entry even before startup, then change its readiness message. Test the route and a disposable task only after approving live model execution.
3. Connect and label each intended work/personal Claude or OpenAI account through AI Connections. For each coding-pod role, choose an agent and inspect its harness, model, named connection, audience, and installed-agent access before allowing work. Exercise a disposable issue with an explicit account binding and inspect run attribution. Revoke the chosen account in a disposable test to verify that the issue blocks without fallback.
4. Integrate this branch with the active governed-cockpit V2 branch after its current work settles. Both branches edit `LocalAgentSetupController.swift`; retain the V2 bundle ID, ports, and data paths from that branch while combining the Splash picker. Run the V2 app smoke script and the focused pod tests after integration. No V1 or V2 app was launched for this branch.

## Verification in this branch

The focused adapter tests use mock HTTP responses and never serve the model. Existing `server/src/__tests__/ai-connections.test.ts` covers named shared grants, private credential homes, provider defaults, and no automatic fallback after revocation; its embedded PostgreSQL fixture did not start on this host during this branch's verification, so those cases remain unverified here. Swift compilation checks the local setup path. Live endpoint and account qualification are intentionally separate from these tests.
