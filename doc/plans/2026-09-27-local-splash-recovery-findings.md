# Local Splash execution recovery findings (2026-09-27)

These are live observations from the separate Splash company in V2. The governed-cockpit worktree was not changed. The one-model Splash queue itself serialized active inference; issue dispatch and recovery still admitted work that should have waited.

- A completed issue could start a duplicate continuation and return to `in_progress` or `blocked`. After SPL-39 was built, browser-verified, and marked done, run `de7bd73e-6e91-4340-a0e1-84e4a2e7d67e` took the model slot for SPL-39 again while SPL-40 waited. The board had to stop the duplicate. Similar queued duplicates occurred after SPL-28, SPL-35, and SPL-36.
- A dependent issue could acquire a queued run before its blocker was done. SPL-22 run `8f03cfbb-a168-4fc7-8fc3-394d646076e8` queued while the shared-core work was still blocked. The board canceled it before model admission. Its old execution blocker then prevented routine reuse, requiring an auditable replacement task.
- Board cancellation of a *running* Splash turn sometimes returned HTTP 500 while the run stayed `running`/`reconnecting` with an operator-cancel error and no active Splash inference (for example SPL-16 run `b31da56e-ae69-4278-8f8c-f9c5bbe01e69`). A graceful V2 app shutdown made the run terminal. Queued-run cancellation returned HTTP 409 even when the run became `cancelled`.
- Cancellation readback can also disagree for an active watchdog turn. Cancel of unnecessary SPL-56 run `33161a71-e928-42fa-8dd5-621b93855d8f` returned HTTP 409 (“provider termination could not be verified”) at 16:20:41 UTC, but a subsequent run read showed `cancelled`, SPL-56 was `done`, and queued CTO coordination run `ce48be72-6786-441b-b5c5-d98f9e56913b` advanced. Splash reported one active decoder. Preserve the 409 uncertainty in the audit; reconcile actual run and provider stop receipts before claiming cancellation failed or reusing resources.
- Periodic recovery sometimes surfaced canceled or board-completed issues as `blocked` or `in_progress` again because older failed-run reconciliation remained attached. The board preserved the clean game commits, documented supersession, and created fresh project-bound issues rather than replay uncertain work.
- A task watchdog review could be marked reviewed after its run was interrupted, without a verified source disposition. SPL-48 reviewed blocked SPL-45 under fingerprint `task_watchdog_stop:cabba13afd9949fc9870fa45629adc224edc1909b85bffb7ae46d8d2e8fbcad3`. Its local run `fd0fec5a-1647-4eaa-bfc3-94c829fee8ba` committed the W/S correction, then made no further tool progress for over eight minutes and was interrupted by graceful app shutdown at 14:27:55 UTC. On restart, SPL-48 was `blocked` with `legacy_execution_requires_reconciliation`, while the watchdog's `lastReviewedFingerprint` matched the stopped source fingerprint. SPL-45 remained `blocked` without a first-class wait until the board attached SPL-49 as a blocker. This is an observed recovery contract violation, not a confirmed root cause; an interrupted review must not certify its source stop as legitimate.
- A stale active run on a source issue that the board had already verified and marked `done` could still create a new watchdog review after restart. SPL-49 was accepted at commit `6151f3f` with 375px browser evidence, build, and 38 tests. Its duplicate `finish_successful_run_handoff` run `23589fc9-153c-4bfa-8660-81e482de6407` was still `running` after the source became `done`; graceful shutdown interrupted that run. Startup then created SPL-50, a `task_watchdog` review for completed SPL-49, and left it `blocked`. The existing source-aware folding rule requires same-run terminal activity, so it may not cover a later board terminal mutation. A fix needs to distinguish authoritative board completion from an unverified run outcome while preserving the run audit and any independent harmful-work evidence.
- A completion-boundary watchdog can also consume the model slot after its source is already `done`, without a restart. Local Coder marked SPL-55 `done` at 16:12:13 UTC after commit `1f0289b` and board-verified browser/build/test evidence. SPL-56 watchdog run `33161a71-e928-42fa-8dd5-621b93855d8f` started at 16:12:55 UTC with `task_watchdog_stopped_subtree`, while a new local CTO coordination issue SPL-57 waited behind it in the one-model queue. The controller should re-read source terminal status at watchdog admission and suppress model review when no independent unsafe-work evidence remains. This is a dispatch/race hypothesis; the exact run and source state are the confirmed evidence.

- Queued child runs diverged from their first-class dependency state under shared-workspace contention. The CTO created SPL-58 (plastic) and SPL-59 (facts) on the same game workspace; the board set SPL-59 `blockedBy` SPL-58 at 16:34:27 UTC, before either took the model slot. At 16:48:40, SPL-58 run `0c84ac00-52f2-4753-8dfe-5483d1db1378` completed with zero model tokens and `skippedStaleTask: "blocked"` even though its issue had no blocker edge. SPL-59 run `cd44ec75-948e-4808-8d15-ec67fcacc316` then entered inference while API readback showed SPL-59 still blocked by SPL-58; it was cancelled before any file write at 16:50:07. SPL-58 subsequently carried `legacy_execution_requires_reconciliation` pointing at that SPL-59 run. The adapter now checks unresolved `blockedBy` relations as an extra final gate, but the status/hold projection and cross-issue recovery reference require a control-plane fix and focused tests on the main V2 branch.
- The task-watchdog classifier can open reviewer work for a dependency wait that already has a healthy live blocker. After local CTO recovery created active SPL-62 and rewired SPL-59 to `blockedBy` SPL-62, SPL-59 was visibly `blocked` on the Coder's live run. Paperclip still created SPL-64, a `task_watchdog` review for SPL-59. Its queued run `f169c9ce-497f-4dca-919b-62d875f922ac` was cancelled before model admission at 17:34:51, and the redundant watchdog was disabled while the first-class wait remained. A watchdog should classify the blocker chain's live path before spending another local model turn on the waiting source.

The relevant code paths appear to include `server/src/services/recovery/service.ts`, `server/src/services/legacy-execution-recovery.ts`, `server/src/services/execution-recovery-resolution.ts`, and the board cancel route in `server/src/routes/agents.ts`. This is a routing hypothesis, not a confirmed root cause. Before changing the governed cockpit, add focused tests for claim-time blocker/status checks, a terminal board-completed disposition, and bounded cancellation/readback of queued versus active local runs.
